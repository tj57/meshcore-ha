### P1 — `str.isdigit()` w parserze mcrpc wywołuje `ValueError` na danych sieciowych

Patrz raport mcrpc §3 P1 — pełna analiza. **Wpływ na meshcore-ha:** `custom_components/meshcore/vendor/mcrpc/parser.py:111,121` jest **identyczna kopia** upstream (`diff` między `vendor/mcrpc/` a `python/mcrpc/` jest pusty — weryfikowane). Każdy incoming packet radiowy przez `_maybe_answer_inbound()` → `_mcrpc.parse(body)` może rzucić `ValueError`, jeśli peer wyśle coś jak `#²` (np. przez błąd w firmware, albo przez intentional fuzzing).

Wyjątek ucieka przez `hass.async_create_task(self._async_send_answer(...))` albo wchodzi do `logbook`, ale HA nie traci stabilności — `async_create_task` łapie `Exception` wewnątrz i loguje. **Wpływ:** log spam + `error` counter w HA, nie downtime.

**Rekomendacja:** poprawki w upstream mcrpc (§3 P1 tam) + **synchroniczna aktualizacja vendored kopii** + test regresji.

### P2 — `B904` w `config_flow.py` (raise bez `from`)

```python
custom_components/meshcore/config_flow.py:233
    except asyncio.TimeoutError:
        raise CannotConnect("Connection timed out")
custom_components/meshcore/config_flow.py:236
    except Exception as ex:
        _LOGGER.error("Validation error: %s", ex)
        raise CannotConnect(f"Failed to connect: {str(ex)}")
```

`B904` domaga się `raise ... from err` albo `raise ... from None`. W tym przypadku `CannotConnect` powinien być z `from err`, bo `asyncio.TimeoutError`/`Exception` nie jest błędem użytkownika, tylko przekładany na HA flow error. Bez `from` łańcuch przyczyn jest przerywany w tracebacks.

**Rekomendacja (bezpieczna, 2 linie):**
```python
except asyncio.TimeoutError as err:
    raise CannotConnect("Connection timed out") from err
...
except Exception as ex:
    ...
    raise CannotConnect(f"Failed to connect: {str(ex)}") from ex
```

### P2 — `services.py:219` — `ast.parse` na dowolnym stringu użytkownika

```python
def _parse_functional_command(command_str: str) -> tuple | None:
    m = re.match(r"^(\w+)\s*\((.*)\)\s*$", command_str.strip(), re.DOTALL)
    ...
    node = ast.parse(f"_{body})", mode="eval")   # ← body z UI service
    pos_args = [ast.literal_eval(a) for a in call_node.args]
    kw_args = {kw.arg: ast.literal_eval(kw.value) for kw in call_node.keywords}
```

`ast.literal_eval` jest bezpieczny (tylko literalne typy), więc **brak exec**. `ast.parse(..., mode="eval")` też nie wykonuje kodu — buduje AST. Ale:

1. `ast.parse` na **arbitralnie długim** stringu z UI może wywołać `RecursionError` albo `MemoryError` (HA API jest dostępny z UI, więc każdy zalogowany user może próbować). Testy `tests/test_services_parsing.py` testują `__import__('os').system(...)` → `None`, więc iniekcja kodu jest wyłączona. Ale `ast.parse(f"_({'x'*1000000})")` wywoła `RecursionError`.
2. `re.match` z `re.DOTALL` na długim stringu z mnóstwem parazytycznych `(` może być wolny (catastrophic backtracking? Nie tu, regex jest prosty `(\w+)\s*\((.*)\)`).
3. Regex nie ogranicza długości.

**Weryfikacja:** testy 26 passed (`test_services_parsing.py`), test na `__import__` istnieje. To jest bezpieczny design, ale **brak limitu długości**.

**Rekomendacja (bezpieczna, 1 linia):** dodać `if len(command_str) > 4096: return None` na początku funkcji. Niewielka wartość, ale załata potencjalny DoS z UI.
